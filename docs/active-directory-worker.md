# The AD Worker

The AD Worker is the only component in ADDS-PIM permitted to change a privileged Active Directory group membership. Every other component - the browser, the Web frontend, the API - can prepare, validate, sign, and authorize a request, but none of them holds the directory rights to act on it. This page describes why that separation exists, how the Worker is reached, how it actually talks to Active Directory, and the verification step that decides whether a request is allowed to be reported as successful.

For the broader request flow this component sits inside, see [identity-and-lifecycle.md](identity-and-lifecycle.md) and [architecture.md](architecture.md). For the concrete rights granted to the Worker's service account and the certificate/mTLS details summarized below, see [security-model.md](security-model.md). For installing and configuring the Worker service itself, see [operations.md](operations.md).

## Why the Worker is a separate, separately privileged process

The privileged AD change is treated as its own security and process boundary, not just another API operation. The Web frontend and the API never receive any rights to modify AD groups directly, no matter how thoroughly they've already validated a request. Only the AD Worker's service account carries the delegated directory permissions needed to add a time-limited group membership, and only on the specific, non-Tier-0 groups it has been explicitly permitted to touch.

This means a compromise of the Web tier or the API does not, by itself, grant any path to changing Active Directory group membership - the capability simply isn't present in those processes' identities. The Worker runs as its own standalone ASP.NET Core/Kestrel Windows Service. It does not run inside IIS, and it does not share an application pool or runtime identity with the Web or API components. In a single-host development or proof-of-concept setup the API and Worker may still run as separate Windows services with separate identities on the same machine; a production deployment is expected to place the Worker on its own dedicated, domain-joined host.

Before any target group can be used at all, the environment is validated for AD's Privileged Access Management Optional Feature, forest functional level, and suitability, and the group's use is bounded by an explicitly permitted scope. At runtime the Worker only ever processes typed commands that have already passed the API's technical checks - the business authorization decision itself (who is allowed to request what) is made by the API before a command is ever sent, as described in [security-model.md](security-model.md). Production Tier-0 groups are never used for development or automated integration testing.

A Worker command always carries the target account's stable directory identity exactly as validated by the API. The Worker never derives the target account from the caller's interactive logon identity, and it never accepts a freely typed account name as a substitute for that validated, typed identity - this closes off a whole class of mistake where the wrong account could end up with privileged access because a name was ambiguous or mistyped.

## How the API reaches the Worker

The API and the Worker communicate over a private HTTPS endpoint protected by mutual TLS: the Worker validates the API's client certificate, and the API validates the Worker's server certificate, so each side authenticates the other as part of the process boundary. "Private" means the Worker's HTTPS binding, host firewall, and network ACLs only allow inbound connections from explicitly listed API server addresses - no browser, end user, or general management network ever reaches the Worker endpoint directly. Certificate identities are kept separate in both directions: the certificate the API uses to call the Worker and the certificate the Worker uses to call back to the API are distinct and are never reused for each other's purpose. Certificate lifecycle and rollover details live in [security-model.md](security-model.md).

Named pipes or Windows RPC were considered for this boundary and set aside because they only work well for processes co-located on the same host, which would complicate deploying the Worker independently. A message queue was also considered and deferred - it would add real infrastructure before the core workflow had even been established, though moving to a queue later remains possible as long as existing command identifiers and replay semantics are preserved.

Every command sent to the Worker is an explicitly versioned, strongly typed contract rather than a free-form request. It carries a globally unique command ID, request ID, and correlation ID, a UTC issue timestamp, a nonce, and a deterministic hash computed over a fixed, canonical representation of the command's fields (the version, the three IDs, the issue time, the nonce, the directory scope, the target account and target group object GUIDs, and the requested TTL, in a fixed order and byte-exact encoding). The Worker recomputes that hash itself before persisting or executing anything, which means the hash detects any substitution of the command's content anywhere along its internal handling path - it is a content-integrity check layered underneath the transport-level protection that mTLS already provides. A command by itself is never trusted merely because its hash is correct: the caller's certificate still has to be on the Worker's allow-list, the timestamp still has to fall inside the accepted freshness window, and the nonce still has to be unused.

The Worker records every received command, keyed by its command ID, request ID, and nonce, before executing it, and returns the same durable outcome if an identical command is retried - so a duplicated click, a network retry, or a replayed signed request cannot cause the underlying AD change to execute twice. A command that reuses one of those identifiers with different content is rejected outright as a replay or concurrency failure. Commands are also rejected if their issue time is in the future or older than a configured maximum age (30–600 seconds, 300 seconds by default) - a short freshness window that sits on top of, and does not replace, the durable replay protection described above. The Worker exposes no general-purpose command-execution capability; only the fixed set of versioned, typed operations its contract defines can be invoked at all.

## Why AD writes only happen through fixed, versioned operations

The Worker never accepts arbitrary commands, free-form script text, executable fragments, LDAP filters, or distinguished names supplied from outside its own typed contract. Everything it can do to Active Directory is one of a small, fixed set of versioned operations with strongly typed, validated inputs and structured outputs - there is no code path that assembles a script or a filter out of caller-supplied strings.

The AD-facing execution logic sits behind an application-owned interface
(`ITemporaryGroupMembershipService`), and neither the domain layer nor the application layer references any LDAP- or PowerShell-specific type directly. That separation is what let the underlying execution technology change without touching business logic: the project's first working implementation of this interface used a signed PowerShell operation, and it remains in the codebase today as a diagnostic and rollback reference, but it is no longer the adapter used in normal operation.

The current default adapter talks to Active Directory directly over LDAP (via `System.DirectoryServices.Protocols`) rather than through PowerShell. Proving out the fixed PowerShell operation first was still valuable - it validated gMSA delegation and the overall execution path in a real environment - but TTL-link syntax, the LDAP controls involved, and Active Directory's own error behavior are protocol-level constraints that are best exercised directly rather than through a scripting layer sitting in between. The direct-LDAP adapter also lets typed data (object GUIDs, not names or strings) flow all the way through the Worker boundary into the actual directory operation, which is a further reduction in the surface available for the wrong object to be targeted.

Whichever adapter is in use, the Worker treats standard output, standard error, and exit codes (or their LDAP equivalents) in a controlled way, respects timeouts and cancellation, and never writes sensitive data to logs. It also records structured results for every execution - the outcome, how long it took, the technical actor that ran it, the command/request/correlation IDs, and which domain controller was used - because a successful process completion on its own is not treated as a successful outcome (see the verification section below). 
Error categorization for both adapters follows the system's shared [operations.md](operations.md) error
catalog.

## How a TTL membership is actually written to Active Directory

Time-limited group membership is not simulated or tracked only in SQL Server and then quietly removed later by a cleanup job - it uses Active Directory's own Privileged Access Management Optional Feature, which lets a `member` link on a group carry an expiration directly in the directory. The direct-LDAP adapter connects only to the one configured, writable domain controller, authenticates as the Worker's group-managed service account using Kerberos/Negotiate with LDAP signing and sealing enabled, and resolves only the typed object GUIDs that were carried in the Worker command - it never accepts or constructs an LDAP filter or a distinguished name from
caller input.

To create a new expiring membership, the adapter writes the link using Active Directory's TTL-qualified distinguished-name form, `<TTL=seconds,DN>`, against the group's `member` attribute. To read a TTL-bearing membership back - both for verification and for the pre-write check described below - it requests the AD DS link-TTL control (OID `1.2.840.113556.1.4.2309`) when reading the group, which is what causes Active Directory to return the remaining TTL alongside the link value; the adapter checks that the domain controller's root DSE advertises support for that control before it ever attempts a write. Only the Worker's service account needs delegated `member`-write permission on the specific, explicitly approved, non-Tier-0 groups it is allowed to manage - it is not given broader directory-modification rights.

Before adding a new membership, the Worker first reads the group's direct membership from the same configured domain controller. If the target account is already a permanent (non-expiring) member, the write is rejected rather than attempted. If the target account already holds an existing TTL membership, that is rejected too - the current behavior deliberately does not shorten, extend, or replace an already-active time-limited membership. This is a conscious tradeoff: it surfaces an already-active membership as a plain business-level rejection instead of risking a write that silently changes an existing grant's expiration in a direction nobody explicitly authorized. In practice this means an operator has to wait for an existing membership to expire before a new request for the same account and group can succeed.

## Read-back verification: the actual success criterion

This is the rule that governs whether a membership request is ever allowed to be marked as having succeeded: **a request only becomes successful once its membership has been read back from Active Directory after the write and positively verified.** A clean PowerShell exit code, an LDAP call that returned without error, or any success response from the Worker's own process is not sufficient on its own - none of those observations are treated as proof that the directory actually ended up in the intended state.

After a write, the Worker re-reads the group's direct membership from the same domain controller it used for the write - deliberately the same controller, not a different one, so that replication delay between domain controllers can never be mistaken for a successful, fully-propagated change. It repeats this read every two seconds for up to thirty seconds. A verification only counts as successful if, within that window, the membership is present, it carries a TTL (rather than having become or remained permanent), and the remaining TTL is both positive and within a defined tolerance of what was requested - no more than the requested TTL, and no less than the requested TTL minus 45 seconds. That tolerance exists purely to absorb the small amount of time verification itself takes; it can never let a longer-than-authorized TTL pass as a match.

Verification specifically checks:

1. That the explicitly authorized target account and group are still unambiguously identifiable.
2. That the expected membership link is actually present.
3. That the membership carries a TTL and has not ended up permanent.
4. That the remaining TTL matches the expected value within the documented tolerance.
5. Which domain controller was used, when each check ran, and how long verification took.

The Worker records the domain controller used, the start and end time of verification, the observed TTL, and every individual attempt - not just the final outcome. If verification times out, the read shows a permanent or missing membership, or the observed TTL falls outside tolerance, the request is not marked successful. It instead follows the ordinary request state machine described in [identity-and-lifecycle.md](identity-and-lifecycle.md), is classified using the shared error catalog in [operations.md](operations.md), and every verification attempt - successful or not - is recorded as an auditable event as described in [audit-and-observability.md](audit-and-observability.md).

## What this component does not do

The Worker does not decide who is authorized to request what - that decision is made by the API against current server-side data immediately before a command is ever sent, and the Worker only executes commands that already carry a validated, typed target identity. It does not accept general-purpose scripts, filters, or account names from any caller. It does not extend, shorten, or silently replace a membership that already exists. And it does not consider a request finished on the strength of its own execution result - only a positively verified, TTL-bearing read-back from Active Directory does that.
